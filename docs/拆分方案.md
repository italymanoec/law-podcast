# 音檔拆分方案

建議把音檔拆成 **每科一個 GitHub Pages repo**，主站 `episodes.json` 的 `audio` 改成同一個 `github.io` 帳號下的絕對網址。播放器可以維持現狀：`index.html` 的播放與離線下載都直接用 `e.audio`。

這份文件只規劃。沒有搬檔、沒有建 repo，也沒有改 `audio/`、`episodes.json`、`index.html`、`sw.js`。大小與集數用 `python3 tools/split_plan.py --compare-batches 30,24,20,33,40` 重算；腳本只讀。

快照對應 `episodes.json` 的 `built`：`2026-10-31 16:42`，147 集，147 個 mp3，沒有缺檔，也沒有沒被引用的檔。每一筆 `audio` 都是 `audio/<id>.mp3?v=<v>`，而且 query 的 `v` 與欄位 `v` 相同。

## 現在這一站還能再放幾批

GitHub 寫明發布出去的 GitHub Pages 站不可大於 1 GB（[GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)）。文件沒有寫這個 GB 是 10^9 還是 2^30。下面用較小的 **1,000,000,000 bytes**，避免把餘裕估高。MB、GB 都用十進位（1 MB = 1,000,000 bytes）。若要改用 1 GiB = 1,073,741,824 bytes，加 `--limit-bytes 1073741824` 重跑。

站點內容（`audio/` + `episodes.json` + 播放器殼，不含 `.git`、`docs/`、`tools/`）：

| 項目 | bytes |
| --- | ---: |
| `audio/`（147 個 mp3） | 716,037,453 |
| `episodes.json` | 2,310,045 |
| 播放器殼（html、sw、圖示、manifest、README、`.nojekyll`） | 30,763 |
| 合計 | 718,378,261 |

上限減掉站點內容，餘裕 **281,621,739 bytes（281.62 MB）**。新的一集會同時增加音檔與 `episodes.json`，平均增量用這兩者的現況除以 147。無條件捨去之後，這一站 **還能再放 57 集**。`docs/` 與 `tools/` 再佔掉幾萬 bytes，扣掉之後集數仍是 57。

「一批」在這個倉庫的 git log 裡大小不一。下面五個有寫明集數的 commit 加總正好 147，批次編號 3、4 沒有對應 commit，不補造。`6e47caf`（第一批前幾集）的集數已含在第一批的 30 裡，不另計。

| commit | 訊息裡寫的新增 | 訊息裡寫的總集數 |
| --- | --- | --- |
| `adcd6db` | 第一批 30 集（民法、刑法、憲法各 10） | 30 |
| `ce5a6e9` | 批次1：12 科 24 集 | 訊息沒寫累計 |
| `d3f57b1` | 批次2：再加 20 集 | 74 |
| `8331022` | 批次5：新增 33 集 | 107 |
| `ebc6207` | 批次6：四科各 10 集 | 147 |

`30+24+20+33+40 = 147`，與最後一筆總集數相同。批次1 的累計訊息沒寫；`74 − 20 = 54`，且 `30 + 24 = 54`。git 上這幾筆 commit 的 `episodes` 筆數是 5、30、54、74、107、147（`6e47caf` 的 5 集已含在第一批的 30 裡）。批次編號 3、4 沒有對應 commit，不補集數。

以這 57 集的餘裕換算：

| 一批有幾集 | 還能再放幾批 |
| --- | ---: |
| 40（最近一批） | 1 |
| 33 | 1 |
| 30 | 1 |
| 24 | 2 |
| 20 | 2 |
| 五批平均（147 集 / 5 批） | 1 |
| 10（批次6 的「各 10 集」） | 5 |

沿用已經上線的整批規模，這一站大約再放 **1 批** 就碰到 1GB。若之後每一批只加 10 集，可以再放 **5 批**（50 集），第 6 批放不下。

最大的單一 mp3 是 `lab-03.mp3`，5,621,963 bytes。GitHub 對單檔是 50 MB 警告、100 MB 拒絕推送（[About large files](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)），目前的檔遠低於那個門檻。另外，本次 `du -sb .git` 是 594,677,668 bytes；倉庫建議值也是 1 GB，但下一階段先碰到的是 Pages 發布檔這 718 MB。軟性流量上限是每月 100 GB，實際流量待查。

把全部音檔搬進另一個 repo，那個站一樣是 1GB，餘裕還是兩百多 MB。要再放很多批，得拆成多個站。

## 做法

主站維持現在的 `https://italymanoec.github.io/law-podcast/`（網址來自 README）。目錄、逐字稿、播放器留在主站。新 repo 只放該科的 mp3，加上一個空的 `.nojekyll`，Pages 從分支根目錄發布。

新 repo 放在同一個帳號下的 project site。`https://italymanoec.github.io/law-podcast/` 與 `https://italymanoec.github.io/law-podcast-civ/` 的 origin 都是 `https://italymanoec.github.io`，瀏覽器把它們當成同一個網站。離線下載的 `fetch(ep.audio)` 因此不必處理 CORS。

`sw.js` 不讀 `episodes.json`。它的範圍是主站路徑，而且路徑裡有 `/audio/` 就略過，不會去攔別的 repo。

相對路徑 `audio/civ-01.mp3?...` 會繼續解析到主站的 `/law-podcast/audio/`。跨 repo 要寫絕對 https。

倉庫裡沒有自訂網域設定。若主站改掛別的網域，或新 repo 放在別的帳號，`fetch` 會變成跨網域；GitHub Pages 預設不帶 CORS 標頭，離線下載會失敗。實際有沒有掛自訂網域：待查。

### 方案 A：每科一個 repo（建議）

每科最終要收到幾集，倉庫裡沒有寫，待查。跟別科共用一個站時，長得快的那一科會把同站其他科一起頂到 1GB，到時還得再拆一次。現在最大的憲法也只佔上限的 10.76%，單獨成 repo 放得下。前綴與科目已經一對一，repo 名稱用 `law-podcast-<前綴>` 即可。

這些 repo 都還沒建立，名稱有沒有被人占用：待查。

具體一筆（民法第 1 集，`v` 維持 `1e553e3cf1`）：

```text
audio/civ-01.mp3?v=1e553e3cf1
https://italymanoec.github.io/law-podcast-civ/audio/civ-01.mp3?v=1e553e3cf1
```

`id` 是 IndexedDB 的鍵，`v` 是離線檔版本。只換網址、不改 `v`，已經下載的檔還對得上，不會強迫重下。

各集頂層字串欄位裡，像網址的只有 `audio`（147 筆）。`subj`、`no`、`title`、`summary`、`dur`、`lines`、`marks`、`articles` 維持原值。

### 方案 B：每 3 科一個 repo

15 科正好整除，得到 5 個站，音檔餘裕是 `5 × 1,000,000,000 - 716,037,453 = 4,283,962,547` bytes，大約是方案 A 的三分之一。想少開幾個 repo 時再用。科目數以後若變了，用 `--subjects-per-repo` 重算，不要沿用這張表。

分組方式：音檔由大到小排序，輪流發到 5 個 repo，避免大科全擠在一起。餘裕用該 repo 目前全部集數的平均大小來除。若之後只加其中一科、而該科比平均大，實際批數會少於表上的數字；各科自己的數字見方案 A。

## 以後真的要拆時

下面是以後的順序，這次沒有做：

1. 在同一個 GitHub 帳號建立上表的 repo，放入該科 mp3 與空的 `.nojekyll`，從分支根目錄開 Pages。
2. 用瀏覽器直接打開一兩個 mp3 絕對網址，確認聽得見。
3. 主站只改對應集的 `episodes[].audio` 前綴，檔名與 `?v=`、欄位 `v` 都留著。
4. 確認主站播放與「離線下載」都打到新網址之後，再從主站刪掉已經搬走的 mp3。

先改網址、新站還沒開，播放會斷。先刪主站檔案、網址還沒改，也會斷。

同一集音檔若日後覆寫，git 會留下舊檔，repo 會比工作區大。上面的預估只算目前檔案大小，歷史會膨脹多少：待查。
